# ad_filter 按需去广告调度设计（设计文档，待实现）

## 背景与问题

当前 `POST /api/ad_filter/process` 是**全量同步处理**：一次性下载所有分片 → 全部检测 → 全部处理完 → 才返回 m3u8。存在三个问题：

1. **起播等待久**：用户要等整部片处理完才能播（全量 OCR 可能要几分钟）；
2. **seek 无效**：无论用户看哪里，都按顺序从 0 开始处理，拉进度条后仍要等前面分片；
3. **复用粒度粗**：整片一个 `sid`，重复播放才复用，但处理粒度是「整片」，无法只复用某一段。

## 目标

**快速起播 + 按需处理 + seek 优先 + 分片级复用 + 最小开销**。

## 核心思路

把「整片一次性处理」改为「**分片级按需处理 + 结果缓存 + 播放位置驱动的优先级调度**」。

- 分片是天然的最小复用与调度单元（HLS 本就按分片拉流）；
- 用户看哪里，就优先处理哪里；没被看的分片尽量不处理；
- 处理过的分片按「分片 URL + 检测器指纹」缓存，跨会话复用。

## 设计

### 1. 分片级结果缓存（复用粒度）

- 键：`md5(分片绝对URL + 检测器指纹)`；
- 值：`{ad_type, hits, 去水印文件路径}`；
- 目录：`{OUTPUT_ROOT}/segments/{md5}/`（去水印文件 + `result.json`）；
- 命中后任何会话直接复用，**不重复下载 / 检测 / 去水印**；
- 处理中并发去重：同一分片同时只处理一次（per-key 锁，双重检查）。

### 2. 会话结构

- `sid = md5(m3u8_url + headers + 检测器指纹)`（与现一致）；
- 会话内存态：有序分片清单（name、绝对 URL）+ 每分片状态机：
  - `pending`（未处理）→ `processing`（处理中）→ `done`（已处理）；
- 结果按「分片级缓存」持久化，会话本身可重建（重启后靠分片缓存兜底）。

### 3. 快速起播：m3u8 秒回 + 动态分片端点

- `POST /process` **立即返回**初始 m3u8，所有分片统一指向动态端点
  `GET /ad_filter/{sid}/segment/{name}`（**不做任何检测就返回**）；
- `GET /segment/{name}` 按分片状态返回：
  - 已处理 + 丢弃 → `204 No Content`（hls.js 跳过该分片，实现「丢弃」）；
  - 已处理 + 去水印 → 返回本地去水印文件；
  - 已处理 + 正常 → 代理透传上游；
  - 未处理 → 触发处理（见下节）。

> 关键：m3u8 一经返回即固定（点播语义），「去广告」由**分片端点内部**动态完成，
> 前端无需反复拉 m3u8，也无需 live 模式。

### 4. 未处理分片的响应策略（等待 vs 广告的权衡）

单分片检测（下载 + 抽 `OCR_FRAME_COUNT` 帧 + OCR）通常 < 1s，远小于分片时长（2~4s），
推荐「**同步检测**」保证首次即去广告：

- **全广告** → 丢弃（`204`）；
- **水印** → 去水印后返回本地文件；
- **正常** → 代理透传。

对网络极差 / OCR 过慢的场景，降级为「**先透传后替换**」：立即代理透传返回，
后台异步处理并写缓存，前端后续（重播 / 回拉）拿到去广告版。两种策略由配置
`AD_FILTER_SEGMENT_EAGER` 切换（默认 eager=同步检测）。

### 5. 播放位置驱动的优先级调度（seek 优先）

- 前端在播放中周期性上报当前分片序号（`POST /api/ad_filter/{sid}/progress`），
  每次 seek 也立即上报新位置；
- 后端维护优先级队列，处理顺序按「**当前分片 → 其后 lookahead 窗口（默认 +10）→
  更远分片**」降序；
- 后台调度器持续按优先级**预取**处理：用户播放到某分片前，它已处理完并缓存，
  请求端点时命中缓存 → 零等待；
- **seek 时**：新位置分片被提到最高优先级、立即抢占处理；原队列尾部（远未来）分片
  降级甚至丢弃，避免浪费。

### 6. 最小开销

- 只处理「被播放 / 预取」的分片；用户只看片头就退出，则片尾分片不处理；
- 预取窗口 `AD_FILTER_LOOKAHEAD`（默认 10）可调，平衡「起播零等待」与「预取浪费」；
- 分片级缓存跨会话复用，多人看同一部片时，后到者几乎零额外开销。

## 与现状的关系

- 本设计是 `ad_filter` 的演进方向，**尚未实现**；当前仍是「全量同步处理」。
- 现有 `engine.process` 的整片 `sid` 复用、代理端点、检测器 / 去水印插件接口均保留，
  在此基础上增加「分片级缓存 + 按需调度」。
